# Generic local process workspace (draft presentation)

Select the owner environment profile `ZENITH_PROCESS_PROFILE=workspace`. The isolated target is `Process-Workspace`, Runtime 8292 and Service 8291. The root page and `/workspace` show the generic editor; installation and local-review profiles retain the deployer. The component is a draft pending the repository's ZenithUI library finalization rule; no Hub component commit is authorized by this document.

The initial page selects no SOP/process/run and creates no stored record. Catalog/get are explicit reads, never native polling. Create an unsaved JSON draft, validate using Frank's pure Runtime contract compiler, review/save through `process.draft.put`, then review `process.publish` with the loaded Runtime resource version and draft revision. Publishing never creates a Run, actor or provider effect. Runtime owns all draft/version business state; Hub keeps only bounded short-lived review objects in memory.

`GET /api/workspace` reads local owner status/configuration hashes. `POST` uses the same numeric-loopback Host/Origin/CSRF checks as the deployer, UTF8 byte/deadline limits, a closed plan/apply envelope, fixed owner executable/root, and no shell. Plans retain canonical command bytes, SHA256, expected_version, request_id, target/configuration binding and a 60-second deadline. Payloads cannot exceed64 KiB including the fixed bridge envelope; JSON nesting is bounded at 24, numbers must be finite and integer-valued numbers must be JavaScript-safe; they cannot select host paths, policy, namespace or executable. Runtime and Frank remain responsible for full contract/compiler validation, authorization, CAS, idempotency and durable command recovery.

Python actions are `workspace-status`, `workspace-prepare`, `workspace-setup`, `workspace-start`, `workspace-stop`, and `workspace-command`. Preparation receives the previous proposal SHA256 when present for CAS and creates only public metadata; setup receives the exact reviewed SHA256 of `config/workspace-setup-plan.json`. Command receives canonical JSON through bounded private stdin (`--request-stdin`) with only `--request-sha256` in process arguments for `{schema:zenith.workspace-command.v1,action,payload,idempotency_key}`. Allowed public Frank actions: catalog/get/validate/draft-put/publish/resume-command. The command payload is retained by Python in its fixed private workspace request directory and passed to the fixed Frank CLI, never treated as a filesystem selector.

The closed public setup plan declares separate canonical Unix-second strings: `not_before` and `not_after` bound the command permission to at most one hour, while `identity_not_after` bounds the machine key lifetime to at most 365 days after `not_before` and cannot precede `not_after`. The preview reads these fields from the same exact bytes whose SHA256 is passed to setup. A longer key lifetime grants no additional operation or permission window. No automatic renewal or key rotation occurs; the owner controls revocation. Native preflight independently checks the actual current time and all authority bounds.

A successful apply retry returns the same in-memory result and does not invoke the child again. Unknown outcomes keep the exact request identity and may be resumed through Frank's durable journal; no automatic new command or provider retry is made. Unresolved process cleanup blocks further bridge dispatch. Native configured does not mean production qualified; run execution/providers stay disabled. Native journal exhaustion is surfaced as an unconfirmed/denied action, with private diagnostics retained by the Python/Frank owner path; the UI never rotates identities or prunes authority history.

Verification uses isolated fake child execution in `tests/deployer/workspace.test.mjs`; it does not initialize custody, start Runtime, write drafts, publish versions or install a profile. Actual complete chain qualification and browser presentation evidence remain separate.

Renewal adds `workspace-renew-prepare`, `workspace-renew`, and `workspace-renew-resume` to the same closed plan/apply lifecycle. Reviews bind public predecessor/successor receipt selection, proposal bytes and all selected native config hashes. Permission status is additive; original setup receipts remain readable when the public successor selector is absent. Expired permission disables signed commands/start while validation and explicit stopped renewal remain available. Partial/cleanup uncertainty permits only exact retained renewal resume when ownership is resolved. Software upgrade stays an explicit pinned-bundle CLI operation. See [the renewal guide](workspace-permission-renewal.md).
