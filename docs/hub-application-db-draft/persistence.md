# Persistence and authority — draft 6

Status: implemented repository and application owner; see integration-validation.json for the qualified migration and launch evidence. The first implementation uses Node's existing `node:sqlite` integration and **one private `objects.sqlite` database**, extended with a revision ledger and Hub application tables. There is no second inventory database, no resource-graph reconciler, and no configurable user index feature.

## Configuration and ownership

The operator supplies `ZENITH_HUB_DATA_DIR` as the canonical private repository directory. The database is `<dataDir>/objects.sqlite`; immutable files are `<dataDir>/representations/{objects,bindings,definitions}/<sha256>.<extension>` and staging is `<dataDir>/representations/.staging/<server-generated UUID>/`. Initial support requires these directories and database to share `st_dev`, on a local filesystem with functioning atomic rename, directory sync and SQLite WAL locking. Network filesystems and a disconnected external volume are unavailable, not an invitation to open an empty database. Root relocation is an explicit offline operator procedure preserving repository identity; API documents cannot supply paths or loader roots. Software may be installed on a different volume; its inspected location is a binding, not the object-storage root.

Reuse the ownership, no-symlink, size and origin/CSRF guards in `src/lib/objects/{store,controller,registry}.mjs` and `src/lib/setup/state.mjs`. Apply them to every directory component and each immutable representation. Do not change permissions on discovered software or profiles. A credential handle resolves only through an owner-configured private provider; secrets and their contents never become RDF or public projection columns.

`HubRepository` owns the SQLite connection, transaction and file-publication protocol. Object, inventory, profile, connection, settings and journal repositories are scoped facades over that connection. They cannot open independent write transactions. The active setup, connection and generic-object controllers delegate to this owner through compatibility adapters. Legacy fallback remains only for unmigrated compatibility paths; activation redirects prevent dual writers.

## Identity and version keys

| Identity | Rule |
|---|---|
| Object identity | Absolute, stable subject IRI. Never a file path/hash or app table name. Untyped named subjects also retain identities |
| Object revision | Monotonic positive integer per subject. Changes when RDF unit content, profile/implementation binding values, applicable definition set or admission changes. Never reset on restart |
| RDF unit identity/revision | Operational lineage ID plus semantic revision. Membership unchanged within a lineage. A changed canonical RDF dataset advances its unit revision and every member object revision. Membership merge/split creates new unit IDs and retires predecessor current units |
| Binding-only edit | New object revision; same unit ID/revision and RDF digest. Other members retain their object revisions; selection still includes all peers of that unit |
| App record revision | Separate optimistic-concurrency counter. Advances on a changed validated projection or operational overlay; rebuild of identical data does not advance it |
| Profile identity | Immutable versioned schema IRI, pinned together with its mapping and definition set; not the named configuration object's identity |
| Representation identity | `urn:sha256:<bytes digest>`; many lexical JSON-LD files may express identical canonical RDF. Byte integrity and RDF integrity are separate |
| Transaction batch | `hub_commits.id`, idempotency key, request digest and repository generation. Can publish many independent RDF units plus binding/operational changes; is not an RDF unit |
| Repository generation | One monotonically increasing committed snapshot number, used by overview/review APIs. Readers observe one SQLite snapshot |

A SoftwareDescriptor denotes retained descriptive information, currently `zn:Artifact`; it is not an invocable software participant. One stable Hermes descriptor is catalog-independent. An installation record describes one copy/version, not a moving release channel. Upgrade to a different installed version creates a new installation record; the operational active-locator alias switches after inspection. Moving the same verified copy updates its location bindings through a new object revision. Keep receipt and discovery aliases to avoid duplicate registration. Do not merge copies solely by software name or endpoint.

## Authorities and physical tables

The complete logical-field-to-column/JSON mapping is `physical-mapping.json`; SQL NULL reconstructs omission, booleans map exactly to 0/1, and structured JSON values retain their schema. The DDL is in `migrations/003-revision-ledger.sql`, `004-application-projections.sql` and `005-application-state.sql`. Owner-pinned runtime copies in `profiles/application-db` initialize staged or fresh schema-5 repositories. Design tests use memory; integration tests use disposable owned roots. Private application documents share the repository commit and retain native/operational bindings without duplicating semantic authority.

- `hub_files`, `hub_definition_sets/pins`, `hub_object_identities`, `hub_rdf_unit_versions/members`, `hub_object_versions`, `hub_commits` establish immutable committed versions and trust provenance. JSON-LD plus schema-validated profile binding files and pinned definitions are object authority. Canonical N-Quads and `hub_profile_values` are verified, rebuildable caches of those files.
- `hub_current_units/objects` establish the current compatible selection. Composite foreign keys prevent a selected object from naming a different selected unit version. The repository additionally verifies exact complete membership before commit, including untyped named subjects. SQL FKs alone do not prove RDF membership or type conformance.
- `hub_object_type_history`, `hub_rdf_links` and `hub_projections` are rebuildable indexes/views. A projection can exist only for a stored validated profile and current object revision. A general stored object needs no dedicated Hub application row.
- `hub_record_heads` owns app concurrency counters. `hub_installation_state`, `hub_service_state`, `hub_inspections`, `hub_settings`, `hub_catalog_entries`, `hub_connections`, `hub_operations`, `hub_setup_drafts` and `hub_adapter_bindings` own their explicitly mapped operational fields. Their values are not independently editable copies of RDF/profile facts. Presence evidence is append-only in `hub_inspections`; `hub_installation_state.latest_inspection_id/presence_json` is a validated latest-observation cache, not a second authority. Compatibility and runtime observations retain their separate operational owners. Inventory computes effective freshness rather than presenting an expired observation as current proof.
- `hub_reference_bindings` pins documentary version references and explicit external references by exact owner kind/revision/field/target. Current references resolve through the current selection. SQL's nullable historical FK enforces exact version existence; conditional type/profile, owner and action eligibility checks belong in the repository. Profiles on retained old versions always use their own pinned mappings; historical cross-object links without an exact pin remain unresolved, never rebound to today's target.
- `hub_identity_aliases` and `hub_legacy_imports` own migration identity/provenance and idempotent source fingerprints. Aliases cannot redirect an existing legacy key silently.

Record-specific semantic fields remain in their selected RDF/profile files; the named application schemas are facades over `hub_projections`, not new ontology subclasses or competing editable tables. Source/build/installation/configuration links use the review-only property vocabulary. No published Core/Infrastructure definitions change. Infrastructure admission remains rejected in the review tool and outside the initial implementation slice; observational Machine/Service descriptions do not grant invocation or process-control authority.

## Constraints and ordering

Physical `user_version` is 2 today. Migration 003 is additive ledger staging; keep existing `units`, `objects`, `admissions`, `imports`, `object_types` and `object_links` until cutover validation. Migration 004 adds Hub projection/operational tables. Freeze legacy writers, perform the synthetic-qualified backfill/dry-run procedure, then enable the new repository writer and update the `ObjectStore` version guard in the same reviewed implementation change. Old binaries must refuse a migrated database. After cutover the old tables are a read-only migration archive. The ObjectStore facade reads/exports through the new ledger and preserves existing API envelopes; it does not consult stale legacy tables for current objects. Generic type/link queries join `hub_object_type_history`/`hub_rdf_links` to the current selection. Scope blank-node labels with a hash of unit identity/revision when combining unit datasets, as the existing codec/store already does. Old independent writes must never resume.

SQL defines primary/composite keys, non-null/positive revisions, catalog `(catalog_id,catalog_key)` uniqueness, software-key uniqueness, exact historical references, new-write observed admission only (with read-only legacy carryover), external service ownership constraints and lookup indexes. Repository validation additionally enforces profile/schema/type correspondence, exact definition pins, current unit completeness, one installed version/source-build agreement, typed config/receipt/evidence references, safe adapter bindings and read-only projection authority. Run the full draft verifier before writes and invariant checks inside the transaction after expected revisions are checked.

All indexes shown are application-owned shipped database indexes. No new user-facing indexing product is implied. Anonymous-only RDF units are stored in the unit ledger without an invented object identity; a named graph IRI occurring only as a graph name or an IRI used only as a link target is not a subject member.

## Pre-existing admitted objects

The draft snapshot verifier and new `commitBatch` commands reject new infrastructure admission. This does not authorize dropping existing admitted objects. Migration uses the existing pinned full bundle/admission validator to preserve their original RDF, bindings, definition/resource pins, policy and provenance in the ledger with `legacy_read_only=1`. The DDL permits non-observation policy only for that explicit carryover path. Generic read/export APIs retain the original policy; this flag is not a fresh admission or invocation grant. Initial writers return `legacy_read_only` for edits, including addition of a Hub profile, until the complete existing admission pipeline has been reused and qualified for that path. If the local Host is such a record, inventory registration requiring an added Host profile stays blocked rather than creating a duplicate Machine or downgrading its policy. Include this in future migration qualification; the observation-only fixtures here do not establish admitted-object conversion support.

## Immutable provenance and first-slice compatibility

An installation’s source/build fields carry explicit `object-version` selectors. Their RDF links expose identity for graph traversal; reference bindings pin the exact documentary revisions. Source snapshot repository identity and commit cannot change under the same snapshot ID. A build’s content identity (ArtifactRef identity/revision, SHA256 and length), exact source pin and applicable platform cannot change under the same build ID. Software association remains stable. Display version/media-type corrections may create a new revision, retaining those identity facts. An installed-version upgrade or provenance replacement creates a new installation description; moving the same verified copy may revise location bindings and requires fresh inspection. Unknown provenance stays absent. The software descriptor remains release/catalog/installation-independent.

The foundation opens a v2 database read-only and does not add ledger tables to it. Only an empty explicitly opted-in root initializes schema 4. The future staging/backfill procedure above is not implemented or applied. Reopening an unsupported definition set fails closed pending a reviewed definition migration. Immutable history and orphan files are retained; cache rebuild is an explicit repository method, not authority recovery from projected database columns.
