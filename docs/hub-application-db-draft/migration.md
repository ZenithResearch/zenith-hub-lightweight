# Migration and compatibility — draft 6

Status: the v2/fresh-root converter is implemented in `src/lib/application/migration.mjs` and exposed by `scripts/hub.mjs`. See [integration.md](integration.md) for executable commands and exact limits. The source map below explains preservation constraints; future receipt/artifact facades are called out separately.

The current general ObjectStore may use `ZENITH_HUB_DATA_DIR`; the legacy setup projector opens `<setupRoot>/objects/objects.sqlite`. Dry-run must inventory **both configured roots**, not assume they are one database. Prefer the configured general store as target. If distinct stores share a subject identity, merge only if canonical RDF/profile/admission content agrees; retain both source roots/backups and use the highest equivalent current revision with its original import provenance. Conflicting content is a cutover blocker requiring explicit review, never last-writer-wins. If no general store exists, explicitly choose `<setupRoot>/objects` as canonical dataDir and persist that choice in server configuration before conversion. API records cannot choose it.

## Identity and duplicate rules

1. Shipped catalog owns stable descriptor IRIs (Hermes recommendation: `urn:zenith:software:hermes`). Existing equivalent descriptors need a reviewed alias, not silent deletion. New local custom descriptors use repository-allocated IRIs.
2. Reuse an existing valid local Machine identity only after the owner/source mapping identifies this host. Otherwise allocate one repository-local Host identity and record the legacy machine alias. Remote resources never acquire this host merely from an endpoint spelling.
3. Allocate installation identities from a persisted mapping of repository + owned receipt/copy/version identity. A deterministic seed in the dry-run reserves the same IDs across retries; production persists the map before apply. A new installed version is a new record. Do not merge by label, provider, endpoint or directory text alone.
4. A native profile's alias includes its owning application/native profile identity and scope. Identical names in different installations/homes remain separate. Never deduplicate credentials by copying their contents.
5. Same legacy source fingerprint replay is a no-op. Changed source bytes under the same identity require a new reviewed migration delta. Conflicting aliases or source/build/host claims stop that item; unrelated objects remain untouched. No automatic deletion of duplicates.

## Dry-run contract

Input: operator-configured source locations, target repository identity, trusted release and a frozen set of source fingerprints. Scan metadata only under existing private-file guards. Output an immutable proposed report containing schema version, source hashes, target/alias map, would-create/update/no-op counts, per-field authority mapping, missing evidence, partial installs, conflicting identities, opaque credential-provider handles, preserved native data paths, quarantined legacy observations, ordinary-unit counts and blocking items. No secrets in public report; retain sensitive original snapshots only in the existing private backup boundary. Dry-run does not install, probe remote services, adopt, rewrite native profiles, start services or change any database.

`migration-prototype.mjs` exercises identity reservation, receipt-not-presence, partial-install uncertainty, external ownership, native handle retention and idempotent replay against `legacy-example.json` only. It is not the complete migration tool or a substitute for unit/bundle import validation.

## Cutover order and rollback

1. Ship reader compatibility and the dry-run command first; old setup/resource readers still own production. Add a server feature flag defaulting to legacy. No dual writable truth. Stop new conversions if root/pins/sources differ from reviewed fingerprints.
2. Operator reviews dry-run; resolve identity conflicts and configured-root ambiguity. Obtain consistent backups of both configured SQLite stores (including WAL through SQLite backup API), setup/receipt/plan files and immutable representation references. Native application/credential backups use their owner procedures; do not export secrets to ontology storage. Record backup manifests, source revisions and repository identity.
3. Quiesce legacy writers and long-running setup actions, reconcile unknown operations without restarting them, checkpoint consistent source snapshots, and recheck source digests. Apply additive schema 003, backfill immutable units/object versions using existing canonicalization/complete-membership semantics (including read-only admitted carryover via the existing full validator), then schema 004 and application bookkeeping. Preserve ordinary objects and exact source provenance. An interrupted backfill resumes by source fingerprint and persisted alias map; it cannot publish an incomplete generation.
4. Validate all mappings, file hashes/RDF digests, complete units, typed/profile consistency, alias uniqueness, source/build agreement, opaque private handles and snapshot counts; compare old/new read results in a read-only shadow report. Any material mismatch blocks cutover.
5. In one repository transaction set writer mode to repository and publish a complete generation. Enable new readers, keep legacy response adapters, and prohibit old direct writes/projector import. Adapt old public command envelopes to the new single owner where safe; otherwise return an explicit unsupported-legacy-write error. Never let old and new writers update separate authorities.
6. First enable inventory reads and software-based entry. Profile/service/connection writes move only in their ordered slices. Retain originals/backups and immutable files. No automatic old-state deletion or GC.

Before repository-mode writes, rollback restores the matching pre-cutover DB/file/config backups and legacy feature flag. After new writes exist, **roll forward** by repairing projections from retained authority; do not restore an old DB and discard new work. A release rollback after cutover requires a compatible reader/writer or a separately reviewed reverse migration/export. Old binaries must reject `user_version>2`. A failed file-staging batch is invisible and retryable; a committed generation is replayed by idempotency key. No migration rollback deletes native application data or undoes unrelated service-side changes.

Production qualification still required: both-root conflict cases, actual legacy bundles/admitted records, source changes during cutover, interruption at every batch boundary, consistent backup/restore, private credential handle continuity and rollback/roll-forward rehearsal. No live conversion has been performed here.
