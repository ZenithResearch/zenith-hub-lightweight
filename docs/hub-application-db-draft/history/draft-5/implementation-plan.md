# Implementation plan and decision register — draft 5

Objective: implement **software inventory and software-based Hermes entry** as the first complete vertical slice. Profile configuration, guide selection, inference/model servers, service health and external connections remain separate capabilities. The object repository stays general-purpose; this is not revival of the rolled-back resource graph.

## Decision register

| ID | Decision | Status / reasoning |
|---|---|---|
| D01 | Installation/software/host/source/build semantic links are RDF-queryable; paths/credentials/model bindings remain separately owned values | User confirmed |
| D02 | One installation record describes one installed version; source/build provenance must agree | User confirmed. Version upgrades create a new installation description and move the active-copy alias only after verification |
| D03 | Presence, adapter compatibility, profile configuration and runtime health are independent | Recorded user requirement. No guide/service/API requirement for local software presence |
| D04 | Every local ontology-typed object has an immutable JSON-LD representation, binding values where applicable and pinned definitions; app rows validate against exact revisions | Recorded user requirement. Matching IDs/hashes alone is insufficient |
| D05 | Generic ConfigurationProfile with Hermes schema composition; inventory/catalog are app data; no user indexes/resource reconciliation | Recorded user scope |
| D06 | One private Node/SQLite database, existing objects.sqlite plus additive ledger/app tables; local same-volume representation staging | Chosen engineering design; one transaction owner avoids competing inventories and enables consistent projections |
| D07 | RDF unit is a complete named-subject/blank-node component with RDFC-1.0 digest; transaction batch is distinct; binding-only updates preserve RDF unit | Chosen from existing codec/store semantics. Untyped subjects included; referenced-only IRIs excluded |
| D08 | Explicit current/exact-history/external reference selectors, with separate action preconditions | Chosen engineering contract; retains history without making stale targets executable |
| D09 | 30s inspection lifetime, boot/monotonic/fingerprint checks; unknown on failed inspection | Chosen conservative initial policy matching existing freshness. Native-layout qualification is future testing |
| D10 | Durable immutable files before one SQLite publication; idempotency ledger; no automatic GC | Chosen engineering protocol; safe orphan files are preferable to dangling committed pointers |
| D11 | Source-fingerprinted dry-run migration, preserved native ownership/history, no blind promotion of old projector records | Chosen migration design; actual root conflicts/evidence are resolved during future dry-run |
| D13 | Exact source/build provenance and immutable identity facts | Snapshot repository+commit, build content+source version+platform and installed-version pins cannot be retargeted on revision; metadata corrections retain original history |
| D14 | Typed inspection writes belong in the internal batch | Server-issued handles authorize exact proof/association writes; candidate inspections create no placeholder object; registration and association commit together |
| D12 | Infrastructure admission/process authority outside first slice; existing published Core/Infrastructure unchanged | Scoped boundary. Full existing admission pipeline must be reused/qualified before later enabling |

No material user decision blocks the **next inventory/entry implementation** under these choices. Deployment on network/cross-volume storage, user-defined indexes, broader admission, arbitrary new inspectors and live migration approval are intentionally outside it. Actual source conflicts found by a future dry-run can block that migration, without blocking implementation of the reviewed dry-run tool.

## First supported objects

Schema coverage for the first vertical slice (not all facades implemented): Host observation, SoftwareDescriptor, SoftwareCatalogEntry, immutable source/build description when known, SoftwareInstallationRecord, inspection/operational state, HubSettings, retained review Plan/Receipt/Evidence artifacts and SetupOperation. First-slice schema support does not imply all future UI/controllers are implemented.

Generic stored objects remain supported without dedicated app rows: ordinary Artifacts, Receipts, Handoffs, Events, Collections, Domains, untyped named subjects and anonymous units. ConfigurationProfile/Hermes specialization, ServiceInstance and Connection contracts are specified now; their full mutation/consumer migration is slices 5–6. No new ontology class is introduced for these SQL/projection boundaries.
