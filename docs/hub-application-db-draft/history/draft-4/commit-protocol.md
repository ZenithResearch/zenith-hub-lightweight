# Publication and recovery protocol — draft 4

Chosen owner: one `HubRepository` writer over the private SQLite connection and immutable representation root specified in `persistence.md`. Filesystem and SQLite are **not** one atomic transaction. Publish durable files first; publish their references and every derived current/app view in one SQLite transaction. Unreferenced immutable files are safe orphans, not current objects.

## Transaction algorithm

1. Authenticate/admit the local operator request using existing origin, loopback, content-type and CSRF checks. Resolve server-owned handles and trusted release definitions. Compute a stable request digest including action, payload, expected revisions, definition-set ID and adapter/catalog pins. Look up the idempotency key: same digest returns the committed response; different digest returns `idempotency_conflict` (409). Do this again inside the write transaction.
2. Read one repository generation. Assemble complete RDF replacement units plus per-object profile values, explicit reference selectors and operational changes. For RDF changes, require every member's expected object revision; a split/merge requires the complete predecessor units and new unit identities. For binding-only changes require the changed object's expected revision, preserve the exact unit version and include all peers in the resulting current selection. Operational-only changes advance app record revisions, not object revisions.
3. Resolve the owner-pinned definition set and mapping snapshots; interpret JSON-LD using the bounded offline codec. Validate recognized profiles even if no app row exists, canonical RDFC-1.0 digest/membership, typed references and exact historical selectors. Validate projections against the object versions, never accept a database label as a second authority. Refuse infrastructure admission in this initial slice. Preserve unrelated generic objects and blank-only units.
4. In `<dataDir>/representations/.staging/<UUID>`, create files with exclusive no-follow handles and private modes. Serialize whole-unit JSON-LD, per-object bindings, definition snapshots and release/mapping manifests. Calculate byte lengths/SHA256 and read back/validate. Bound sizes/work using existing codec limits. `fsync` every file before it can be referenced. Store no secrets in the representation. Do not accept a root/storage key from an API caller.
5. Under the repository's single writer lock, promote each file to its content-addressed destination on the **same filesystem**. Never overwrite nonmatching existing bytes; verify and reuse a matching immutable file. Sync destination directories (and newly created parent directories) after rename. Only then may SQLite reference the files. Initial support rejects cross-volume staging/rename, unsupported directory sync, symlink traversal and network storage; no copy fallback. Use `PRAGMA journal_mode=WAL; synchronous=FULL; foreign_keys=ON`, `fullfsync=ON` on supported macOS SQLite builds. These requirements define the design; actual power-loss behavior still needs platform qualification.
6. `BEGIN IMMEDIATE`. Recheck idempotency, active definition/adapter/catalog pins, repository generation, expected object/app revisions and action preconditions. If stale, roll back and return 409; already promoted files remain harmless orphans. Insert the batch commit record and immutable ledger entries, including canonical unit digest and complete member list. Insert new object/profile versions and exact definition pins. Delete affected rebuildable projection rows before changing current-object composite keys (readers still see the prior SQLite snapshot), then publish compatible `current_units/objects`, type/link caches, validated Hub projections, operational state and operation result in the same transaction. Enforce FKs and complete-selection/type/profile/reference invariants before COMMIT. For RDF changes update all member heads; binding-only updates can leave peer object revisions unchanged.
7. Commit SQLite. Only a committed generation is visible. A reader opens a SQLite read transaction, obtains generation and all version pointers from that snapshot, then verifies required immutable files (or uses a previously verified immutable-file cache for that exact content identity). Missing/corrupt referenced bytes return `repository_integrity_failure` (503); never return an unvalidated projection or silently fall back to a legacy file.
8. Acknowledge the persisted result. If the response is lost, retry with the same key returns the original result and generation with `replayed:true`. Repeating a mutation with a new key still requires current expected revisions, so it cannot silently duplicate an installation.

The repository lock serializes in-process work; SQLite's write lock and expected-generation check handle competing supported processes. External SQL/file writers are unsupported. Do not hold a SQLite transaction while downloading, building, inspecting a slow remote service or running an installer. Those actions have separate durable operation journals and return results to the repository.

## Crash-point matrix

| Crash point | Reader-visible state | Restart recovery | Same-key retry |
|---|---|---|---|
| Before/during staging write | Old generation only | Ignore incomplete `.staging` files; retain or remove only server-owned unreferenced staging after a lock/age check | Recreate and verify staging |
| After write, before byte/schema verification | Old generation | Unverified bytes cannot be referenced; repeat verification | Same request, no result yet |
| After verification, before file fsync | Old generation | Treat staging as nondurable and revalidate/rewrite | Safe repeat |
| After file fsync, before rename | Old generation | Verified staging may be reused after hash and definition checks | Safe repeat |
| After some renames, before directory sync | Old generation | Rehash any surviving destination; absent files are restaged; no database pointers exist | Safe repeat |
| After all directory syncs, before SQLite BEGIN | Old generation; durable orphan files possible | Reuse only verified matching bytes | Safe repeat |
| Inside SQLite transaction, before COMMIT | Old generation; SQLite rolls back incomplete batch | Keep files; reopen/recover WAL using SQLite, not hand-editing it | Repeat expected-revision validation |
| COMMIT outcome uncertain to caller | Either complete old or complete new generation | Query idempotency record after SQLite recovery; committed record is authoritative | Return original result if committed; otherwise repeat safely |
| COMMIT succeeded, before acknowledgement | Complete new generation | No mutation replay; return persisted result | `replayed:true` |
| Referenced file missing/corrupt after commit | Repository unavailable for affected reads/actions | Preserve database/WAL/files; report integrity failure and restore verified backup; do not regenerate authority from app columns | Block until repaired |
| Installer/native profile side effect completed, result not committed | Operation is applying/unknown; no false success | Reconcile owned receipt/output identity and inspect before recording outcome; never rerun external side effects blindly | Existing operation ID, reconcile rather than reinstall |

A managed install and its final app publication cannot be one filesystem/SQLite transaction. Before launching the existing pinned adapter, persist `applying` with the exact plan/driver digest and destination handle. After completion, independently inspect the installed output, retain a typed receipt/evidence object and commit its installation description. Ambiguous crashes become `reconciliation-required`. A partial receipt or old `installed:true` flag is not current presence proof. Profile adapters similarly write a new managed native generation, validate it, then publish its binding; keep the prior generation. External profiles/credentials/history remain owned by their application and are not rewritten.

## Retention, deletion and repair

Initial implementation **does not implement automatic immutable-file GC**. Retain all current and historical object files, unit files, bindings, definitions, plans, receipts, migration snapshots and orphan content-addressed files. Deleting an application row does not delete an object or its files. A future GC requires reachability from every committed historical/current version and journal, a quarantine interval, writer synchronization and independent verification; it cannot be inferred from the current selection alone.

Back up through SQLite's supported consistent backup API under a write pause/checkpoint boundary and copy all referenced immutable files plus the trusted definition release. Back up private native application stores separately under their existing ownership rules; do not copy credentials into JSON-LD. Restore a matching DB/files set, preserve repository identity and validate before enabling writes. Drive reconnection must reopen and validate the same repository identity, never create a substitute at an accidentally empty mount point.

Required production fault injection: every matrix boundary, disk-full during staging/commit, denied fsync, lost acknowledgement, concurrent stale writers, context/schema substitution, symlink races, volume disconnect, corrupt file and interrupted backup. These are implementation acceptance tests, **not claimed as passed by this design package**.
