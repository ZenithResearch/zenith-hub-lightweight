# Repositories and wire contracts — draft 4

Status: specified interfaces for implementation, not live routes. `api.schema.json` defines closed request/response envelopes. Reuse current local operator admission, endpoint/credential guards, pinned catalog/adapters and reviewed plan/apply controls. Do not expose browser-selected executables, filesystem roots, schema loaders, receipts or process-control authority.

## Repository interfaces

All methods receive a server-owned repository/definition context. IDs in these signatures are IRIs unless explicitly called an opaque handle. Every mutation takes `{idempotencyKey, expectedGeneration, expectedObjects, expectedRecords}`; creation expects revision zero for a planned new identity. The repository allocates stable identities during review and retains the allocation in the plan. Same key/same request returns the same IDs; aliases enforce repeat registration across a new key.

| Method | Inputs | Output / side effects |
|---|---|---|
| `inventory.read({softwareRef?,hostRef?,after?,limit=100})` | Bounded filters; limit 1–200 | Read-only snapshot generation, descriptor/installations, independent presence/compatibility/profile/runtime facets. No scanning, networking or writes |
| `hub.readOverview()` | None | Read-only generation, gallery resources and entry eligibility; no service polling or setup mutation |
| `inspections.inspectSoftware({softwareRef,hostRef,candidateHandle?,scopeHandle?})` | Local host plus server-owned discovery/scope handle | Bounded read-only filesystem inspection; ephemeral handle/proof expires after 30s. No install, adoption, permissions change, profile/config read, service start or DB write |
| `inventory.registerExisting({inspectionHandle,...expected})` | Fresh server proof for an actual copy | Retained descriptor/source/build references as known, installation Artifact/JSON-LD + binding, inspection evidence, app projection/operational observation and aliases in one repository commit. Always `management:external`; registration does not adopt |
| `inventory.recordManagedOutcome({operationId,adapterOutcomeHandle,...expected})` | **Internal** result of the reviewed pinned installer, owned receipt and fresh post-install inspection | Retained Receipt/evidence, installation record and operational outcome. Not a public client-fabricated receipt endpoint. Partial/unknown outcomes are journals plus unknown presence |
| `profiles.upsertNamed({softwareRef,profileId?,installationRef?,name,profileKind,nativeProfileHandle?,credentialRefs?,modelBinding?,mode,...expected})` | Generic or Hermes schema; external native handle for describe-only, or planned private generation for create/update managed | Versioned Artifact RDF/profile values and projection; adapter effect is explicit in review. Generic profiles reject AI fields. External describe-only never copies/replaces native credentials/history. Updating a running managed profile requires prior explicit stop; return `profile_in_use_requires_stop` rather than stopping it |
| `services.register({softwareRef,label,installationRef?,profileRef?,hostRefs?,...expected})` | Observed existing service | Observation-only ServiceInstance and app projection; public registration stays externally owned/unmanaged. Native managed service registration is internal to a separate approved adapter outcome. Registration neither starts nor admits a callable service |
| `connections.save({connectionId?,targetRef,targetScope,adapterRef,endpoint,enabled,credentialRef?,endpointPolicyRef?,...expected})` | Adapter ID and opaque private credential/policy handles | Application-owned binding, no new ontology class or inferred local installation. Check target type/currentness, adapter-supported endpoint/auth/capabilities and privacy. A disabled historical connection remains retained but cannot execute |
| `settings.enterHub({inspectionHandle,...expected})` | Fresh verified local Hermes presence only | Update app `entered_at`; no guide/profile/server/model requirement. Unsupported adapter revision can still satisfy software presence; configuration controls explain incompatibility |
| `reviews.create(command)` / `reviews.apply(planId,digest,key)` | Closed commands below | Persist a plan Artifact and reviewed journal; apply rechecks every precondition and publishes a commit or durable applying job. No arbitrary command strings |

Expected-generation protects a review snapshot; expected-object revisions protect complete object/unit updates; expected-record revisions protect operational/configuration bookkeeping. Apply also rechecks catalog/driver/definition pins and inspected filesystem fingerprints. A no-op replay returns original revisions. Operational changes do not mutate RDF. Semantic/profile edits always use the object repository.

## HTTP surface

| Route | Contract | Read-only / errors |
|---|---|---|
| `GET /api/hub/inventory` | `InventoryResponse`; filters above | Read-only; 400 invalid/duplicate query; 503 store unavailable/unverified |
| `GET /api/hub` | `OverviewResponse` (versioned replacement; legacy v1 adapter until cutover) | Read-only. Unlike today's controller refresh, no hidden probes |
| `POST /api/hub/inspections` | `InspectionRequest → InspectionResponse` | Read-only filesystem inspection; 403 remote host/unsafe scope; 200 includes present/absent/unknown facts with reasons; 503 unreadable repository |
| `POST /api/hub/reviews` | `ReviewRequest → ReviewResponse` | Persists reviewed plan/journal, not installer/model/service execution. Reuse existing 120s plan expiry and driver/catalog digests |
| `POST /api/hub/actions` | `ApplyRequest → MutationResponse` | 200 committed metadata mutation/replay or 202 applying operation ID. Actual installs invoke existing pinned adapters only after review |
| `GET /api/hub/operations?id=<IRI>` | Retained SetupOperation plus exact selectors | Read-only, 404 missing. Current/historical journals retained; no implicit historical action target |

Common errors are `{schema, error:{code,retryable,details?}}`. 400 malformed/unknown fields; 403 origin/CSRF/ownership; 404 unknown identity/handle; 409 `stale_generation`, `stale_object_revision`, `stale_record_revision`, `idempotency_conflict`, `plan_expired`, `plan_changed`, `inspection_expired`, `operation_target_not_current`, `profile_in_use_requires_stop`; 422 `type_mismatch`, `profile_mismatch`, `reference_unresolved`, `unit_incomplete`, `definition_untrusted`, `installation_provenance_mismatch`, `unsupported_adapter`; 503 `repository_unavailable`/`repository_integrity_failure`. Never expose secret contents/private logs in errors. Transient 503/unknown-outcome retries use the same key and reconciliation rules, not blind side-effect replay.

## Reference policy by purpose

`reference-policy.json` and `ReferenceBinding` specify exact owner kind (`object` revision or application row revision), field pointer, target identity and selector (`current`, `object-version`, `external`). Missing selectors mean current **only for current objects/app records**. No resolver searches any loaded history as a fallback.

| Purpose | Retained snapshot validation | Action precondition |
|---|---|---|
| Current semantic software/host/source/build/profile links | Resolve current object and expected type/profile, or explicit exact/external declaration. Source/build must agree when resolved. Independently validate stored bindings even with no app row | Mutable actionable associations must be current; require complete expected unit revisions. Do not execute an external unresolved association |
| Historical object links | Validate local RDF/profile facts with that object's own pinned definitions/mapping. Cross-object traversal requires exact historical selector or external declaration; otherwise expose unresolved | Never silently bind to current; no action from historical view |
| Enabled local connection | Current selected target of the adapter's expected type; loaded history insufficient | Fresh endpoint/auth/capability guard and authority check; no implicit process ownership |
| Disabled/stale connection | Exact historical version or explicit unresolved external target allowed | Re-review and bind current target before enabling. Historical binding cannot become actionable by toggling a boolean |
| External connection | Explicit `targetScope:external-unresolved`; known contradictory local type still rejected | Approved endpoint/credential policy and adapter probe required; successful API reachability does not prove local installation |
| Reviewed/applying operation | Retain current/exact/external target selectors for the journal; missing references must be explicit | **Starting** reviewed work requires current targets, matching expected revisions, unexpired plan/driver/definition pins and authority. A retained stale plan can be valid data while ineligible to apply. Applying jobs are reconciled, never restarted from an historical target |
| Complete/cancelled journal | Exact historical targets, retained plan and receipts allowed | Documentary; cannot execute |
| Plans/evidence/config content | Artifact or subclass. Current/exact version allowed. Explicit external is unresolved, not a type claim. Config content cannot be self-reference | Content used for an action must be locally available, verified and pinned; no automatic fetch through a bare IRI |
| Receipts | Receipt or subclass, including exact retained history. Existence is not proof of current software presence | Documentary acknowledgement, never a substitute for inspection |

Snapshot validation checks shape, trust, current selection, known types/profile consistency and explicit resolution mode. Action guards additionally check current expected revisions, freshness, endpoint policy, credentials, supported adapter capabilities, ownership/admission and plan expiry. The small executable `actionPreconditions` probe covers revision/selector eligibility only; it is not the full authorization implementation.

## Internal batch interface

`HubRepository.commitBatch(batch: RepositoryBatch): Promise<{commitId,generation,objectVersions,recordRevisions,replayed}>` accepts exactly `commit.schema.json`, not a browser request. A batch has an idempotency key/expected generation/trusted definition set, complete `unitWrites`, exact `retireUnits`, `objectWrites`, `appWrites` and per-owner reference bindings. It contains documents/values, **not storage roots or destination keys**. The repository derives serialization and content-addressed paths.

`expectedRevision:0` creates a new identity; otherwise match the committed current revision and assign `newRevision=expectedRevision+1`. For unit semantic no-op, reuse the current unit revision rather than creating a new unit write; binding-only object writes reference it. For unchanged object versions no objectWrite is needed. RDF-changing unit writes include all member object writes, every expected member revision and complete predecessor retirement where membership changes. An appWrite's `value.revision` is `expectedRevision+1`; typed `value.objectVersion` must reference the selected object/profile and reconstruct exactly. The final selection is previous current state minus retired/replaced units plus these writes, validated in full. An operational-only batch can have no unit/object writes. Omitted referenceBindings preserve existing selectors for unchanged owners; writing a new owner revision supplies its complete outgoing explicit selectors (no accidental inherited current binding).

A retained review plan is a `zn:Artifact` with the `api.schema.json#/$defs/ReviewPlan` application profile (identity/types validated; structured plan fields authoritative in the profile value). Register/pin that profile in the owner-selected application definition set; it creates no ontology subclass and needs no dedicated app row. The plan is referenced by exact object revision; its digest, expected-generation baseline and pins are checked before apply. Creating the plan/journal itself advances repository generation: store the resulting post-review generation as the apply baseline and exclude only those known plan/journal writes when comparing the reviewed mutation's original object/record expectations. Return the post-review generation in ReviewResponse. A separate request cannot modify any reviewed target unnoticed.

Legacy-only ingestion is a separate internal migration interface: `migration.ingestLegacyBundle({sourceFingerprint,bundle,reservedAliases,expectedGeneration})`. Validate through the existing full bundle/registry pipeline, retain the source policies and pins, and publish non-observation versions as `legacy_read_only=1`. It cannot be called through public commands or used to mint a new admission. New app-profile additions to these objects are rejected until that full update path is separately qualified.

Application-only records do not acquire ontology versions merely to preserve a journal. For a completed operation on a removed Connection or other bookkeeping record, retain the exact old request/record snapshot inside its versioned plan/receipt Artifact and mark the now-unresolved target identity explicitly external/documentary. Do not invent an object revision for an untyped application row. Reusing that target requires a new current binding and review. A review snapshot includes only reference bindings whose owner object/app revisions are included; the repository retains older owner metadata for audit.
