# Software installation evidence — draft 4

Presence answers whether a particular software copy is installed on this host within a declared inspection scope. It does not answer whether the adapter supports that revision, a profile is configured, the service is running, an inference backend is available or the Hub owns lifecycle control.

## Evidence and classification

The server's inspection adapter receives a software descriptor, the repository's local Host identity and opaque candidate/scope handles. It enumerates only configured bounded roots/known launchers, using read-only no-follow file handles, bounded bytes, ownership checks and resolved path/fingerprint metadata. It does **not** execute a discovered launcher/import untrusted source, read profile secrets, install, chmod, adopt, start, or contact a model backend. No recursive whole-disk search. A missing/unreadable mount or directory is unknown, not not-found.

- **Present:** at least one recognized installation layout is verified from current files: descriptor-matching source/package metadata, actual entry point and required environment/launcher markers for that layout. Use published file/inventory digests where available; retain which identity/provenance checks passed. A revision outside adapter support may be present only when descriptor identity is independently established by an owner-trusted installed manifest/package signature or accepted publisher inventory. A lookalike name/layout or self-asserted stamp alone remains unknown. Adapter compatibility can still be unsupported/unknown. A launcher path alone, a forged/unverified receipt or a source directory without a usable installation layout is insufficient.
- **Absent:** all configured candidates in the declared, completely inspected scope are positively not-found with their containing roots accessible. Say “not found in inspected locations,” not “does not exist anywhere on this machine.” This may describe the descriptor/host scope without inventing an installation object. Do not report absence based on an exception, permissions error, partial inspection, failed hash or missing volume.
- **Unknown:** any failed/incomplete inspection without a verified copy, incompatible metadata format, inaccessible path/volume or partial installation. A failed identity/hash check is unknown/tampered evidence, not successful presence; retain the reason. Inspection support is a separate fact, not a fourth presence state.

An old successful install receipt is provenance. A profile/native home, remote Hermes connection, guide API response, successful chat or service process is not current installation evidence. A running service could refer to deleted files or a remote host. New inventory entry must not inherit today's `welcomeLandingState` shortcuts that count connect-mode instances or old installed flags as local software presence.

## Freshness and provenance

Proof contains `inspectionHandle`, local Host/software identity, declared scope and scope completeness, state/reason, adapter digest, filesystem fingerprint digest, server `bootId`, server `observedAt` and `validUntil`. The handle is server-issued and bound to these facts; clients cannot submit their own “present” proof. `api.schema.json` defines its public shape; private evidence retains per-candidate outcomes without leaking secret contents.

Use a **30 second** maximum lifetime, matching existing discovery freshness. During one process lifetime use a monotonic elapsed clock; wall clock is retained for audit only. Reject future skew beyond 5 seconds, backwards-clock anomalies, proof from another boot, incomplete/changed fingerprints, remount/device changes or expiration. After restart refresh inspection before entry/register/apply. Recheck fingerprints at action apply; a still-young proof does not excuse changed files. Routine GETs do not scan or mutate; explicit inspection refresh supplies the proof. After storing an observation, its historical state remains truthful at its timestamp while the *current effective state* becomes unknown when expired.

Registration of a verified discovered copy remains `management:external`. “Managed” requires a successful reviewed owned installer outcome plus post-install inspection; it is not inferred from presence. Compatibility qualification uses pinned contract/runtime files separately (`verifySoftware` is existing evidence for this adapter boundary). Configuration support can be blocked while software presence still permits entering the Hub. Guide setup and running API remain optional, separately tracked resources.

`presence-prototype.mjs` and its synthetic checks exercise classification/freshness rules without touching the filesystem. Actual safe inspection of native layouts, races, permissions, volume changes and unsupported revisions remains an implementation qualification requirement.
