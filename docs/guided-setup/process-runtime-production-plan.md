# From a clean clone to one completed Case workflow

Implementation plan · 25 November 2026

## What a new user should experience

On a supported Apple silicon Mac with Git, Node 24, npm and Python 3.12, a user clones the Lightweight Hub repository, runs the README's setup command, and opens the loopback URL that the launcher prints. In Hub they choose **Set up local process example**, review the component downloads and destination, and apply. **Run example** then shows one Service Management Case, its Runtime run, the step completed by Frank, and the recorded output. Stopping and reopening Hub preserves the result.

Proposed entry point after cloning: `npm run setup`. This is a new command to implement. It should install the locked Hub dependencies and reuse the existing launcher. The setup and verification path must work with an empty home directory, empty caches, no sibling repositories, and no hand-edited environment file. The first milestone is an explicitly labeled local development example using disposable inputs and a deterministic local integration. Production activation has its own acceptance criteria below.

## Gaps in the checkout

- The launcher defaults to 4318 and prints its URL. The README tells users to copy an environment example that selects 4208 and a Homebrew-specific Python path. Make the launcher the single source of defaults and detect the supported interpreter before installation. [README](../../README.md) · [Environment example](../../.env.operator.example) · [Launcher](../../scripts/hub.mjs)
- The native demo manifest pins Service Management and Runtime. The base Mac release also includes Frank, with no actor enabled by default. The Docker CI smoke registers a Runtime actor and checks for an empty work list. None of those checks establishes that a new user can deliver a Service handoff and see Frank complete its step. [Native demo manifest](../../profiles/process-native/profile.json) · [Mac release](../../profiles/process-macos/release.v1.json) · [CI](../../.github/workflows/deployer.yml)
- Hub already supports review/apply, a private installation root, monitoring history, and a reversible Runtime upgrade. Reuse those paths. The upgrade rehearsal consumes prebuilt wheels. A clean clone needs a reproducible way to obtain every selected artifact. [Installer](../../profiles/process-macos/installer_bundle.py) · [Upgrade rehearsal](../../tests/hub/runtime-upgrade.test.mjs)

## Implementation order

| Change | Source work | Acceptance |
| --- | --- | --- |
| 1. Capture the clean-clone failure | Add a macOS smoke job that checks out tracked files into a path with spaces, uses an empty user-owned setup root, and follows the documented commands. Record the first failing stage and actual URL. Reuse this job in every subsequent change. | The job identifies which prerequisite, artifact, startup step or workflow transition failed. It cannot pass by finding a developer installation or a listener from a previous run. |
| 2. Ship one setup entry point | In the Hub launcher and package scripts, detect prerequisites, run the locked install, prepare the private root and launch Hub. Use one port selection rule for the server, UI and printed URL. Turn the environment example into optional overrides. Put the tested clone and setup commands first in the README. | One command after cloning reaches Hub Settings. A second invocation finds the same healthy instance. An occupied port, unsupported platform or missing Python produces a specific remedy before creating a partial component installation. |
| 3. Package the three components together | Extend the existing local demo recipe with compatible Service, Runtime and Frank pins from their owning repositories. Produce a versioned bundle from those pins in CI. Give Hub one reviewed manifest for packages, hashes, configuration and the bounded example. Verify it through the existing installer. Support the same manifest for an offline bundle. | Starting with empty caches, Hub can install all three components using only declared sources and prerequisites. Repeating setup preserves identities and data. A corrupt or incomplete download fails at the named artifact and can be retried. Before release, verify the archive is readable with the access available to the intended user. |
| 4. Run one workflow through the real component interfaces | Ship a one-step process and a deterministic local Frank integration. Use the existing explicit development authority in an isolated loopback profile. Service Management accepts an example request, converts it to a Case and persists a handoff for a pinned process version. Its delivery worker submits that handoff through the Runtime client. Runtime admits it and creates the run. A configured Frank Actor claims the step and submits its result. The Service projection reads the committed progress. | A fresh installation produces one Case, one accepted handoff, one run, one completed step and the expected output. Re-delivering the same handoff returns the same run. Reopening the workspace shows the retained result. Case closure remains a Service lifecycle decision. |
| 5. Make success and failure visible in Hub | Expose the first-run actions in the existing guided setup. Show progress and timestamps for installation, Service handoff, Runtime admission, Frank execution and projection. Read each outcome from its owning service or receipt. Keep host resource samples in monitoring history. | The user can find the Case, run and output in Hub. With admission closed, Hub identifies the blocked handoff. With Frank stopped, it identifies eligible work awaiting an actor. The operator reconciles interrupted work against the retained action and reports any unresolved effect. |

Hub owns packaging, orchestration and display. Fix a delivery defect in Service Management, a run or admission defect in Runtime, and an execution or result defect in Frank. Pin the corrected component in Hub and rerun the same black-box workflow. This keeps the example on the interfaces a real installation uses.

## Launch and invocation contracts

The local recipe must pin a callable version of each component. Its fixed example is a single step that uppercases an ASCII string, with input `{"text":"hello hub"}` and committed output `{"text":"HELLO HUB"}`. Package a deterministic Frank integration for this operation, or add it in Frank if the pinned distribution lacks one. Verify that its Actor advertises the exact capability and resource required by the step. This profile runs entirely on loopback in explicit development mode. secS-server, native Wallet/Transfer review, production credentials and external providers are outside this milestone.

| Boundary | Implementation and test obligation |
| --- | --- |
| **Hub sets up the definition. Runtime publishes and owns it.** | Include the example draft, intended version ID and expected compilation hash in the pinned recipe. Through the public Runtime SDK, Hub looks up that ID with `version.get`. If absent, use `process.draft.put` and `process.publish` with the correct draft revision, expected versions and retained request IDs. Read back and compare the exact `process_id`, `process_version` and `compilation_hash`. Reuse a match on setup retry. A conflicting existing version stops setup with a diagnostic. |
| **Hub launches Service and Runtime. Service delivers the handoff.** | Give Runtime its own database and loopback port. Launch Service with its own database, explicit `--runtime-endpoint` pointing at this Runtime, a distinct `--projection-database`, and `--poll-runtime` to enable both delivery and projection workers. Select development authority explicitly on both processes. Verify both worker statuses through Service. Drive `request.create`, `request.qualify`, `request.accept`, `request.convert`, `case.plan`, then `case.plan.approve` with the exact published pin and typed inputs. Service validates the pin against Runtime and owns the durable handoff. Wait for Service’s acknowledged run ID. |
| **Hub invokes bounded Frank commands. Runtime owns the claim and commit.** | Hub’s local operator runs the installed `frank-executor` as a bounded child with an example-only configuration, Actor, Runtime origin and Frank journal. At setup, validate configuration and register that Actor. For an example action, call `work`, select the eligible item for the acknowledged run and expected step, and pass its exact run, step, operation and scope to `execute` with the Actor, stable claim request ID, lease and wait bound. If the item is absent, report the last observation and poll within a bound. Persist Frank’s effect reference when available; inspect its journal and Runtime through their owner interfaces on restart. |
| **Interruption test for this invoker** | Terminate the bounded Frank child after the integration has durably recorded the result and before Hub records command success. Restart the operator. Inspect the existing attempt, effect and committed output. If completion is outstanding and the lease is valid, invoke Frank’s `resume --effect-key` for that effect. If already committed, adopt the verified receipt. Count integration dispatches and committed outputs; each must remain one. Exercise expired-fence or ambiguous-effect recovery separately and expose an unresolved state whenever the owner cannot establish the outcome. |

Confirm these contracts against the selected release pins when assembling the bundle. The upstream specifications are [Runtime’s public API](https://github.com/ZenithResearch/process-runtime/blob/2efdf9672a279ae924c095cc357d15ccad754bf1/docs/api-and-executor-v1.md), [Service’s worker composition](https://github.com/ZenithResearch/service-management/blob/bc084f2a875f7af333d7f01db01c94a9f93c1672/docs/runtime-workers.md), and Frank’s `docs/operations.md` in the selected Frank source revision.

## Run identity and recovery

Before the browser can dispatch **Run example**, Hub persists a pending action ID in the example workspace and gives the browser that ID. Clicks, transport retries and reconnects use it. Before the first Service mutation, persist the chosen request, Case and plan-revision identities and the stable development subject. Before **each** mutating call, save its exact request body, expected version and request ID; record the acknowledgement separately. Service keys idempotency by verified subject and request ID. Replay uncertain calls with the original bytes and subject. A known rejection or version conflict requires an explicit disposition. Keep Service’s original outbox and Runtime’s claim and receipt identities throughout recovery.

| User action | Required behavior and assertion |
| --- | --- |
| Reopen Hub | Read the retained action and owner observations. Reopening dispatches no workflow. The same Case, run and output are shown after a full stop/start. |
| Retry after losing the Run example response | Drop the browser response after Hub accepts the action; also interrupt Hub after Service commits a mutation but before its acknowledgement is saved. Retry or reconnect with the same action ID. Recover the exact Service result and handoff. Assert one Case, one run and one committed output for that action. |
| Choose **Run new example** | Only this explicit action allocates a fresh action ID and fresh Service identities. Running the same fixed input produces a second distinct Case and run with one output each. The original remains inspectable. Protect the new-action request against duplicate submission too. |

## Tagged-release browser gate

On a clean supported macOS runner, check out the tag into a path with spaces. Start with an empty user-owned root and empty caches. Use only the tagged README to launch, and navigate a real browser to the URL printed by that launcher. In the browser follow **Set up local process example → Review → Apply → Run example**. A proposed or different port, hidden CLI setup, preexisting definitions, or direct API substitutions for UI actions invalidate the rehearsal. Capture the review, selected artifact versions, action ID, visible result and fresh monitoring observations.

After the browser shows the fixed output, independently verify it with read-only owner interfaces:

1. Use Service’s `request.execution`, `case.plan-history` and `case.summary` to correlate the request, Case, approved revision, exact process pin, acknowledged handoff and run. Wait within a documented bound for a current projection.
2. Use Runtime’s `version.get`, `run.get`, `attempt.get`, `output.get` and `receipt.get` to match the pin, run, step, attempt, fence, Actor and committed output. Compare the output value and digest with the fixed fixture.
3. Use Frank’s inspection interface and the test integration’s dispatch evidence to tie the same Actor, effect and attempt to one dispatch. Cross-check IDs and counts with the browser result. The Service projection supplies progress; Runtime supplies the canonical output.
4. Run all three identity scenarios above and the bounded-child interruption test. Retain browser evidence and a redacted correlation report for the tag. A passing launcher smoke test is the exit criterion for the first PR; these end-to-end assertions are the release gate.

## Production and existing installations

After the clone path passes, use the same workflow to qualify a production profile. Build on the existing workspace flow for a scoped Service identity, a reviewed handoff and derived Run, a Frank Actor, and explicit admission. Exercise expiry, revocation, denial outside scope, and recovery. Identify any missing issuer at the specific call that fails. Transfer is a candidate for owner approval if that deployment selects it. The local example requires neither Transfer nor personal credentials. Selecting production must never fall back to development authority. [Workspace activation](../provider-workspace-activation.md)

Keep existing roots on the reviewed migration and rollback path. A first-time setup encountering an existing installation should offer to open it or create a separate example workspace. A release is ready for new users when a second person or clean macOS runner can follow only the tagged README, reach the expected output, reopen the original run after restart, and intentionally start a distinct example. Verify upgrade and rollback against a populated disposable copy as a separate release check.

**First PR:** add the clean-clone smoke job, reconcile the launcher defaults, and land the proposed setup command with its tested README instructions. Its deliverable is a reachable Hub from a bare checkout. The three-service workflow becomes the release gate in steps 3–5.
